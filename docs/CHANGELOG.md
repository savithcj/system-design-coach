# Changelog
- Initial build pack assembled.

## Step 1: scaffold and port the core
- Vite + strict TypeScript + Vitest + Playwright (real Chrome via `channel: 'chrome'`). Scripts: `dev`, `build`, `test`, `evals`, `e2e`.
- `src/core/`: `events` (pure `append` with NodeMoved coalescing, log serialise/parse), `reduce` (+ `reduceUpTo` for replay), `layout` (grid, free slot, tidy), `geometry` (ports, curves, snapping), `mermaid`, `report`, `actions` (default/copy names, connect toggle).
- Ported t2/t4 scenarios that are logic rather than DOM (naming, copy names, connect toggle, delete cascade, coalescing, tidy pinning, layout stability, snap radius). DOM scenarios move to Playwright in Step 2.
- Added tests: replay prefix equals live state, log round-trip, arrows stay inside the canvas for every pair of grid boxes, connecting never moves a box.
- Deliberate differences from the prototype:
  - `NodeRenamed` now writes `label` (docs/04); `to` from old logs is still read.
  - The reducer enforces one arrow per ordered pair, no self-arrows, no dangling arrows, and ignores empty names.
  - The old regex judge, hints and ReAct loop are NOT ported (replaced by the engine in Steps 5 to 7). The report has no "reference design" or score yet; the baseline returns in Step 6, shown only after the session is finished.
  - `CLAUDE.md`: Chrome path replaced with `channel: 'chrome'` (the old path does not exist on macOS).

## Step 2: port the UI exactly
- `src/ui/` ports the prototype's board, picker, chat, top bar, Details dialog, report view and resizer to plain DOM/SVG. CSS and the HTML shell are the prototype's, extracted verbatim (`src/ui/style.css`, `index.html`).
- Verified side by side in real Chrome (light and dark): empty and populated boards are pixel-identical except 63 px of sub-pixel text rendering in the top-bar tab labels.
- Playwright (`tests/e2e/board.spec.ts`, 16 tests): the `chrome_check.py` regression (connecting must not move boxes; arrows inside the canvas), picker, rename (double-click, F2, Enter, blur), hover-only dots, click and key connect, arrow select and delete, copy/paste, key moves and coalescing, drag with dots following, Tidy, problem switching and Start over, chat, splitter, report with rendered diagram.
- Self-hosting: Mermaid is bundled from npm and imported lazily when the report opens; Inter is bundled via `@fontsource/inter`. No runtime request leaves the app.
- Deliberate differences from the prototype:
  - Ctrl/Cmd+C on a focused box now copies only. The prototype also started a connection (the `C` handler ignored modifiers).
  - Chat records the learner's message but the coach does not answer yet: the prototype's regex router and judge are gone, and the engine arrives in Steps 5 to 7. The opening message still shows.
  - The report omits score, requirement check and reference design for now (see Step 1).
- Dev only: `window.__sdc` exposes read-only `log()` and `state()` for Playwright. It is absent from production builds.
- Known quirk kept on purpose: a click within 60 ms of finishing a drag is ignored (it swallows the click the browser fires after pointer-up).

## Step 3: arrow labels, node notes, undo/redo
- **Core**: `EdgeLabeled`, `NodeNoteUpdated`, `UserActionUndone`, `UserActionRedone`. Undo is an event: the reducer skips the undone group, the log only grows (`core/undo.ts`).
  - One undo step per committed edit (Enter or blur), and a box's creation plus its immediate naming is one step. A drag or a burst of arrow-key moves within 1.5 s is one step (it is one coalesced event).
  - Redo restores the most recently undone step and is cleared by any newer board edit; chat does not clear it. Chat, coach events and the opening message are never undone.
  - The report keeps what happened and adds "Undid: ..." / "Redid: ..." lines.
- **Tests**: reducer tests per event, undo of every edit type including delete (box, note and arrows return), redo rules, replay with undo in the log, and a seeded model-based property test (k undos land on the state after n-k edits; m redos on n-k+m).
- **UI**
  - Arrow label: double-click (tap-timing, like boxes) or Enter/F2 on a focused arrow; Enter or blur saves, Escape reverts, empty clears. Labels are drawn in a layer above the boxes with a halo, because the grid gap is narrower than a label.
  - Node note: `N` on a focused box, the hover/focus note icon, or click the note. Enter or blur saves, Shift+Enter adds a line, Escape reverts. The note is as wide as its box and sits on a side whose dot has no arrow (below, else above, else right, else left; `noteSide`), so it never hides a connection. It moves with its box.
  - Undo/redo: Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z, announced through the live region ("Undid: Added ..."). Inside a text field the browser's own text undo wins.
- **Keyboard access to arrows** (not specified in the docs; needed because arrows were mouse-only): `E` on a focused box moves focus to one of its arrows; arrow keys switch between arrows; Enter/F2 labels, Delete removes, Escape returns to the box. Clicking an arrow now focuses it, so Enter/F2/Delete work right after a click. The arrow layer is no longer `aria-hidden` (arrows are real controls with labels). The hidden help text lists the new keys.
- Known limitation: on a very short gap between two boxes the label's halo covers the whole arrow. Dragging the boxes apart restores it.
- Verified in real Chrome (light and dark) including the keyboard focus halo on a selected arrow and the note editor. The screenshots caught two layout bugs the tests could not: notes covering neighbouring boxes and labels clipped by boxes.

## Step 4: stage pill and contract notes
- **Core**: `StageChanged` and `ContractNoteUpdated` events; state gains `stage` and `contract`. `core/stages.ts` holds the five stages with their targets (5, 2, 5, 12, 10 min), cumulative per-stage time (`stageTimes`, exact for a given log) and event-to-stage mapping. `engine/contract.ts` parses a block deterministically: strips bullets and numbering and splits at the first line that is only dashes (`---`); everything after it is below the line. No intent guessing.
- **Stage pill** (top bar): `1 Requirements .. 5 Deep dives` as a radiogroup with a quiet clock on the current stage (cumulative, `aria-hidden` so it is not re-announced). Clicking or pressing Enter/Space chooses a stage (appends `StageChanged`, opens that stage's blocks, tints its zone, announces "Stage 3, API."). Arrow keys, Home and End only move focus: choosing is an event, so it is deliberate. Nothing is hidden by a stage; contract notes stay editable in every stage.
- **Contract notes**: a left column on the dotted canvas, four collapsible plain-text blocks (Functional, Non-functional, Core entities, API / data flow). Collapsed by default except the current stage's blocks. Stages 1 to 3 tint their blocks; stages 4 and 5 tint the board. No placeholder or instructional text, per the UX rules; the engine's `REQ_NO_OUT_OF_SCOPE` rule will teach the `---` convention.
  - Typing never re-renders the board, moves focus, or floods the log: the panel is built once, input schedules one `ContractNoteUpdated` 400 ms after the last keystroke, and blur saves immediately (so switching problems or opening Details never loses text). A field being typed in is never overwritten.
  - Block open/closed is UI state, not an event.
  - On narrow screens (under 900 px) the notes stack above the board and the pill takes its own row.
- Contract note edits and stage changes are **not** board-undoable (inside a field Ctrl/Cmd+Z is the browser's own text undo). This is a choice: the docs list board edits as undoable and note typing is already covered by native undo.
- **Report** is now organised by stage: a time-per-stage table against the targets, the steps grouped under the stage they happened in (empty stages get no heading), then the contract notes with "Out of scope" separate, then the diagram. The same in LaTeX (a `tabular`, `\subsection*` per stage). Time is measured to the last event, so a given log always renders the same report.
- Layout: the canvas is now a row (notes column 240 px, board beside it), so the board is narrower than in Step 2. The board width is read from its own column (`#boardCol`).
- Tests: the e2e clock tests freeze Playwright's fake clock before load, since it otherwise keeps ticking in real time.
- Not done here (Steps 5 to 7): the coach does not yet read the stage or the notes; `RuleFired/Resolved` and the per-rule flags in the report arrive with the engine.

## Step 5: engine
Pure TypeScript in `src/engine/`, no DOM, no model. Nothing in the UI uses it yet (Step 7).
- **Pipeline**: `evaluate(state, problem, lens)` returns every violation on the board as it is; `selectMove(...)` picks one coach move; `scriptedText` words it; `checkReply` (grounding gate) vets any wording, scripted or model.
- **Rules**: the 18 starter rules of docs/05, one file each in `engine/rules/`, listed in `registry.ts`. Wording is ours. Each rule has `hints.l1` (a question), `l2(v)` (narrower, uses the learner's own box names), `l3(v)` (the approach), a `spoilers` list that L1/L2 and model replies may not contain, and `resolvedBy` text for the report. Term lists live in the rule files and are matched by `engine/text.ts`.
- **Events** added to the log type: `HintRequested {level, ruleId?}`, `RuleFired`, `RuleResolved`, `CoachReplyRejected`, and an optional `move` on `CoachResponded`. They never change the board. `syncRules(log, violations)` returns only the changes, so each issue is fired once and resolved once; `historyOf(log)` reads what the coach already did (no hidden memory).
- **Selector**: earliest stage first, then severity, then the problem's challenge order. Rules of a later stage wait, which is the premature-optimisation guard (in stage 4 the deep dives are flagged but not raised). Never the same rule twice in a row unless "Stuck?" was pressed. Hint level rises only on request (1, 2, 3; level 3 sets `needsConfirm`), or one level narrower when an unresolved rule comes back in a later stage. Learner `level` (mid, senior, staff, default mid) gates rules via `minLevel`: a mid-level learner still sees `DD_LOCK_STORE_OUTAGE` and `DD_SEARCH_PRIMARY_STORE` flagged but is not coached on them. Affirms a stage once, only if it has content and nothing flagged.
- **Grounding gate**: ghost components (a technology from a closed list in `engine/lexicon.ts` that the learner has not written anywhere, aliases such as Postgres/PostgreSQL treated as one), spoilers (the rule's own, plus the problem's `stageSpoilers` for stages not reached yet; a confirmed level-3 hint may use the rule's own), and shape (one question, length cap, no code fences, no numbered lists, no "the answer is").
- Deviations from the doc sketch, on purpose: `check` returns a `Finding` and `evaluate` fills in rule id, stage and severity; violations carry `subjects` (the learner's own names) so wording never invents a component; `evaluate` takes the stage from `state` and returns all violations regardless of stage; problem-specific rules (`needsChallenge`) only run when the problem lists them in `challenges`; stage spoilers are keyed 1..5 and mean "not before this stage".
- Judgement calls inside rules (all deterministic, all tested): `REQ_VAGUE_NFR` fires on a vague term with no number and no scope word; the "no stated priority" part of the doc is covered by `REQ_CAP_UNSCOPED`. `HLD_NO_ENTRY_POINT` fires when a client reaches two or more servers directly and none looks like a gateway or balancer. Reachability for `HLD_UNFINISHED_PATH` ignores arrow direction, so a reversed arrow is not reported as a missing route. `API_NO_COVERAGE` matches on shared nouns after dropping a plural "s".
- Not yet: box properties read from notes (replica counts, QPS) are not used, because no starter rule needs them; they will come with the first rule that does. The learner-level control in Details is deferred to Step 7 together with the first UI that uses the coach.
- Tests: 103 new (every rule has a firing, a silent and where relevant a valid-alternative case; selector, level calibration, tracking, hints vs spoilers, gate).

## Step 6: problems and fixtures
- **Problem format** (`src/problems/`): `Problem` = title, prompt, `stageRubrics` (what good looks like, report only), `requiredPaths` (by category), `challenges` (problem-specific rules with stage, trigger, order and why it matters), `stageSpoilers` (keyed 1..5, "not before this stage"), `nudges`, `scaleNotes`. URL shortener, rate limiter and news feed are ported; Ticketmaster is new (7 challenges). The Ticketmaster tab is labelled "Tickets" and the stage pill now takes its own row below 1300 px, because a fourth tab pushed Finish onto a second row.
- **The reference design is isolated by construction**: `baselines.ts` holds the prototype's target designs (and the Ticketmaster one) with their rationales. Only the report (Step 9) may import it; a test fails if anything else does. The engine, coach and prompts cannot see it. Nothing is pass/fail against it.
- **Nudges** (the prototype's per-component questions, plus ours for Ticketmaster) are kept as the wording for "what is missing" when no rule flags anything. `nextNudge` matches by category and count only, so any technology satisfies it; it is wired in Step 7.
- **Fixtures**: 21 JSON event logs in `evals/fixtures/`, authored with `npx tsx evals/author.ts` (a few lines per scenario). They cover every starter rule at least once, five valid-alternative cases (the same need met with other technologies or wording must not flag), level calibration (mid vs senior on the same board), and "never the same rule twice in a row". The prototype's `t2.js`/`t4.js` are UI scripts; their coverage is already in the Playwright suite from Steps 1 to 4, so they did not become fixtures.
- **`npm run evals`** prints one row per fixture for layer A (flags exact), B (move, move-about, moves not allowed) and C (every move plus level 1 and 2 wording for each flagged rule, through the grounding gate with the scripted coach), then the spoiler-leak and ghost-component rates, and exits non-zero on any failure or any leak. Currently 21 of 21, 0.0% and 0.0%. Layer C takes a `Phraser`, so Step 8 plugs a model in without changing the runner. Vitest runs the same harness, plus tests that the harness itself fails when it should.
- Engine changes found while writing fixtures: `API_NO_COVERAGE` now leans on nouns only one requirement uses (a shared noun such as "events" could hide an uncovered requirement); `HLD_PREMATURE_OPTIMISATION` is now `warn` and ranks before `HLD_UNFINISHED_PATH`, so a lone cache gets "why this now?" rather than "your route is unfinished".
- The example fixture in docs/05 expects `probe_bottleneck` for `API_USER_ID_IN_BODY`; the engine says `challenge_assumption`, and the fixtures follow the engine.
